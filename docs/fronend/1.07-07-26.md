## 1) หน้า Access Logs (admin) — `/logs`

**ทำอะไร**
- ยกระดับหน้า `/logs` จาก mock ธรรมดา → **admin dashboard**: การ์ดสถิติ 4 ช่อง + ตัวกรอง (ค้นหา/หลักฐาน/action/result) + drill-down รายหลักฐาน (คลิกเลข evidence เพื่อดูเฉพาะชิ้นนั้น)
- จำกัดเมนู/หน้าเฉพาะ admin (tri-state guard) และย้ายเมนูไป adminItems ใน Sidebar
- สร้าง `services/http/accessLog.service.ts` เป็น "สัญญา" (contract) ชี้ `GET /api/access-logs` ไว้ล่วงหน้า

**ทำไมต้องทำ**
- โจทย์: admin ต้องดูได้ว่า "ใครเข้าถึงหลักฐานชิ้นไหน เวลาใด" ซึ่งเป็นหัวใจของระบบหลักฐานดิจิทัล (auditability)

**ไฟล์:** `app/(dashboard)/logs/page.tsx`, `services/http/accessLog.service.ts`, `services/index.ts`, `components/layout/Sidebar.tsx`

**backend ต้องทำต่อ**
- `GET /api/access-logs` (admin only) รองรับ filter `evidence_id`/`user_id`/`action`/`result` + pagination — reuse join เดิมใน `dashboard_repository.get_recent_activity()` (ตาราง `access_logs` มีอยู่แล้ว)
- **Write-side:** บันทึก `access_logs` จริงเมื่อมีการเปิด/ดาวน์โหลดหลักฐาน (ดึง `ip_address`/`user_agent` จาก `Request`) — ปัจจุบันไม่มี evidence endpoint ใด ๆ เขียน log เลย

## 2) หน้า Dashboard — เพิ่มมุมมอง admin — `/dashboard`

**ทำอะไร**
- **ลบ** การ์ดสถิติ 4 ช่องด้านบน + Quick Actions (ตามที่ตกลงว่าไม่จำเป็น)
- **เพิ่ม** ส่วนเฉพาะ admin "ภาพรวมการเข้าถึงหลักฐาน": สถิติ 3 ช่อง (การเข้าถึงทั้งหมด/ผู้เข้าถึง/หลักฐาน) + อันดับ Top 5 (หลักฐานที่ถูกเข้าถึงบ่อยสุด + ผู้ใช้ที่เข้าถึงมากสุด) พร้อมแถบสัดส่วน

**ทำไมต้องทำ**
- ให้ admin เห็นภาพรวมการเข้าถึงได้ทันทีจากหน้าแรก ไม่ต้องเข้า `/logs`

**ไฟล์:** `app/(dashboard)/dashboard/page.tsx`

**backend ต้องทำต่อ**
- endpoint สรุป/aggregate ของ access logs (นับตาม evidence, ตาม user) เพื่อป้อนสถิติ+Top — ตอนนี้คำนวณจาก `mockLogs` ฝั่ง client

## 3) หน้าสร้างคดี + สิทธิ์ตามยศ/ลำดับบังคับบัญชา — `/cases`, `/cases/new`

**ทำอะไร**
- `/cases` เขียนใหม่เป็น client: กรองคดีตามสิทธิ์ (`visibleCases`), ปุ่ม New Case เฉพาะหัวหน้า, wire ค้นหา
- `/cases/new` ฟอร์มสร้างคดี + guard ตามยศ
- `/cases/[id]` เพิ่ม guard การมองเห็น (คดีนอกความรับผิดชอบ → "ไม่มีสิทธิ์")
- Helper กลาง `utils/caseAccess.ts`: `POLICE_RANKS`, `canCreateByRank` (เกณฑ์ชั้นสัญญาบัตร), `canCreateCase`, `subordinatesOf`, `canSeeCase`, `visibleCases`
- `utils/caseStore.ts`: localStorage store ให้สร้างคดีแล้วเห็นผลจริง
- `mockUsers` + ปรับ `created_by`/`assigned_officer` ของ mockCases เป็น username

**กติกาที่ตกลง**
- **สร้างคดีได้ = ตามยศ** (ชั้นสัญญาบัตร ร้อยตำรวจตรีขึ้นไป) และไม่ใช่ admin
- **หัวหน้า** เห็นคดีของตัวเอง + ของลูกน้อง · **ลูกน้อง** เห็นเฉพาะที่ถูก assign · **admin** เห็นทุกคดี แต่**สร้างไม่ได้**

**ทำไมต้องทำ**
- สะท้อนการทำงานจริงขององค์กรตำรวจ (สายบังคับบัญชา) + คุมการเข้าถึงข้อมูลคดีตามความรับผิดชอบ

**ไฟล์:** `utils/caseAccess.ts`, `utils/caseStore.ts`, `app/(dashboard)/cases/page.tsx`, `cases/new/page.tsx`, `cases/[id]/page.tsx`, `utils/mockData.ts`

**backend ต้องทำต่อ**
- `POST /api/cases` (สร้างคดี) — บังคับสิทธิ์ฝั่ง server: อนุญาตเฉพาะยศชั้นสัญญาบัตร, ห้าม admin
- `GET /api/cases` — คืนคดี**ตาม scope**: admin=ทั้งหมด, หัวหน้า=ของตัวเอง+ลูกน้อง, อื่น ๆ =ที่ถูก assign
- ต้องมี **การจัดลำดับยศ** ฝั่ง server (เพิ่มคอลัมน์ rank level หรือ mapping) เพราะตอนนี้ `rank` เป็น string อิสระ ไม่มีลำดับ

## 4) การจัดการสายบังคับบัญชา — ให้ admin เป็นเจ้าของ

**ทำอะไร (มี 2 รอบ)**
- รอบแรกทำไว้ 2 ทาง (admin ตั้งตอนสร้าง user + หน้า `/team` ให้หัวหน้าเลือกลูกน้องเอง)
- **รอบสอง (สรุป): ตัด self-service ทิ้ง** — ลบหน้า `/team` + เมนู My Team, และให้ **admin แก้ "หัวหน้า" ของผู้ใช้ที่มีอยู่แล้วได้** ผ่าน dropdown ต่อแถวในหน้า Manage Users
- `utils/hierarchyStore.ts`: เก็บ mapping `username → หัวหน้า` ใน localStorage (admin เขียน, `caseAccess` อ่าน)

**ทำไมต้องทำ (หลักการ)**
- สายบังคับบัญชาเป็น**ตัวกำหนดการมองเห็นข้อมูล** จึงควรมีแหล่งความจริงเดียวที่ admin คุม
- **least privilege / separation of duties**: ถ้าหัวหน้าประกาศลูกน้องเองได้ = self-granted access (ยกระดับสิทธิ์ตัวเอง) → ช่องโหว่
- อำนาจที่เหมาะกับหัวหน้า = การ **assign คดีรายชิ้น** (scope แคบ ตรวจสอบได้)

**ไฟล์:** `utils/hierarchyStore.ts`, `app/(dashboard)/users/page.tsx`, `components/layout/Sidebar.tsx` (ลบเมนู)

**backend ต้องทำต่อ**
- เพิ่มคอลัมน์ **`users.supervisor_id`** (self-FK) เก็บสายบังคับบัญชา
- endpoint **แก้ไขผู้ใช้** (เช่น `PATCH /api/users/{id}`) ให้ admin ตั้ง/แก้ `supervisor_id` ได้ (admin only)
- ให้ `GET /api/users` (หรือ endpoint ย่อย) คืน `supervisor_id`/ชื่อหัวหน้า

---

## สรุปสิ่งที่ backend ต้องทำ (รวม)
1. **Cases API** — `POST /api/cases` (สร้าง, บังคับสิทธิ์ตามยศ, ห้าม admin) + `GET /api/cases` (คืนตาม scope หัวหน้า/ลูกน้อง/admin)
2. **Access Logs API** — `GET /api/access-logs` (admin, filter) + เขียน log จริงตอนเข้าถึงหลักฐาน (ip/user_agent) + endpoint สรุปสำหรับ dashboard
3. **User hierarchy** — คอลัมน์ `users.supervisor_id` + endpoint แก้ผู้ใช้ให้ admin ตั้งหัวหน้าได้
4. **Rank ordering** — วิธีจัดลำดับยศฝั่ง server (rank level) เพื่อใช้ตัดสิน "ใครสร้างคดีได้"
5. **Authorization** — ปัจจุบัน backend มีแค่ `admin` vs not; ต้องเพิ่มการเช็คสิทธิ์ตาม **ยศ + สายบังคับบัญชา** ให้ตรงกับตรรกะฝั่ง frontend (`caseAccess.ts`)
